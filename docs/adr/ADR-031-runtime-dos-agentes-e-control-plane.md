# ADR-031: Runtime dos agentes, pipelines retomáveis e Control Plane do motor

Status: aceita (implementada e verificada com LLM roteirizado; execução real depende de `ANTHROPIC_API_KEY`).

## Contexto
Os agentes 1–8 já existiam como funções com validação pelo código (ADR-030). Faltava o que os transforma em runtime operável: registro, versões de prompt, execução com tempo e retentativa, pipeline com dependências e retomada, auditoria de decisão e uma interface que explique tudo. Princípio: **o LLM propõe; a aplicação valida; o motor determinístico decide; o Control Plane explica; a auditoria prova o que aconteceu.**

## Decisões
1. **Reuso, não reescrita.** `runAgent` continua o único ponto de chamada ao modelo (cache determinístico, orçamento, auditoria em `agent_run`). O runtime o estende: resolução de prompt por agente (`RuntimeContext.resolve`), tempo-limite por agente, retentativa de falha *transitória* (429, 5xx, rede, tempo) com recuo, cancelamento cooperativo, teto de chamadas (`CallGuard`) e rastreio (`pipeline_run_id`, `correlation_id`, `prompt_version_id`, `duration_ms`). Estados de execução: `succeeded`, `failed`, `invalid_output`, `timed_out`, `cancelled`, `not_configured`. Falha permanente (401/403/rejeição) não repete; saída inválida tem as duas correções internas e depois vira `invalid_output`.
2. **Cabeçalho comum com contexto explícito.** O runtime acrescenta ao cabeçalho do pack um bloco gerado (tenant, pacote de domínio e versão, agente, versão do prompt, versões de contrato, `execution_id` = `agent_run.id`, `correlation_id`). Valores são sanitizados (sem chaves de template, sem quebra de linha, tamanho limitado); `fillTemplate` continua lançando para variável sem valor.
3. **Registro de agentes** (`agents/registry.ts`, espelhado em `agent_definition`, só INSERT, nova linha quando o hash operacional muda): id estável, contratos v1, tempo, retentativas, lote (A03–A05: 20–50; A06–A08: uma página por chamada; A02 é por entidade), dependências e o que o código valida depois de cada agente.
4. **Registro de prompts** (`prompt_version`): DRAFT → ACTIVE → DEPRECATED; corpo imutável (UPDATE só de estado e regressão); mesmo corpo não duplica; uma ATIVA por (tenant, agente, pacote); gatilho recusa transição inválida; validação de placeholders; versão criada no Control Plane só ativa com regressão aprovada registrada; rollback volta à substituída mais recente; tudo auditado em `decision_audit`. O arquivo do pack continua a origem versionada em git (`seedFilePrompts`); sem versão no registro vale o arquivo e isso aparece como `source = file`.
5. **Pipelines explícitos** (`pipeline_run` + `pipeline_step`): página = eligibility → explain (A05) → blueprint → blueprint_semantics (A06, só se o código não fechou a diferenciação) → serp_gate (SERP ou exceção humana, ADR-025) → recipe_qa (A07 + Q1–Q13 em código + A08) → quality_gate. Tópicos = inventory (A01) → proposals (A02) → intents (A03, lotes) → combination_review (A04, o código aplica). Cada passo tem dependências, chave de idempotência derivada do artefato anterior e estado persistido; reexecutar a mesma correlação reaproveita o que já concluiu com a mesma chave. Falta de entrada vira passo `SKIPPED` explícito; falta de chave vira `BLOCKED` com `blockedExternally`.
6. **Lotes com isolamento.** `runBatched` divide por bisseção o lote que falha; só o item que quebra fica como falha individual.
7. **Autoridade do código.** A04 só recomenda: o código absorve uma combinação apenas se não houver blocos de dados exclusivos, com desempate determinístico entre irmãos, e nunca regride estados avançados; cada veredito vai a `decision_audit` (`decided_by = code`, recomendação guardada, aplicada ou recusada). O **Quality Gate Engine** (`qualityGate`, função pura) dá o desfecho final `APPROVED` (apto à revisão humana; nada é publicado), `BLOCKED` ou `NEEDS_REVIEW`; nenhum agente aprova a própria saída; o verificador (A08) só reprova mais.
8. **Real × simulação.** `pipeline_run.mode` é `real` ou `test_simulation`; simulação (LLM roteirizado) só existe em testes e é exibida em destaque. A interface de produção nunca simula: sem chave, os passos de agente ficam bloqueados externamente.
9. **Control Plane** (`/engine`): Agentes, Prompts (registrar rascunho, ativar, rollback), Execuções e Inspetor de saída, Pipelines (executar uma página, cancelar, abrir passos e auditoria), Tópicos, Elegibilidade, oportunidade no motor (decisão + explicação, blueprint, recipe, QA) e o registro de andamento. Leitura só de funções tipadas de `packages/api`, por `withTenant`; escritas só por ações do servidor com identidade da sessão. Bancada de desenvolvimento: `scripts/dev-engine.sh` (banco descartável, sem login, nunca em produção).

## Consequências e limites
- Não há execução de modelo real: a qualidade dos prompts e a aderência dos modelos **não estão validadas**; a regressão de prompts registra resultado mas o executor de regressão ainda não existe.
- Honrar `Retry-After`, persistir os tópicos propostos pelo A02 e montar a entrada do A01 do catálogo real continuam pendentes (ver `ENGINE_PROGRESS.md`).
- Migration 0019 (aditiva): `agent_definition`, `prompt_version`, `pipeline_run`, `pipeline_step`, `decision_audit` + colunas de rastreio em `agent_run`; RLS forçada, aplicação sem DELETE, UPDATE só nas colunas de estado.
