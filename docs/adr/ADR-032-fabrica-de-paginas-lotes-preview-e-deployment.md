# ADR-032: Fábrica de páginas — métricas, pipeline observável, lotes, preview e Deployment Center

Status: aceita (implementada e verificada com LLM roteirizado e API da Vercel simulada; execução real depende de `ANTHROPIC_API_KEY` e de um projeto Vercel conectado).

## Contexto
O Control Plane do motor (ADR-031) mostrava o runtime dos agentes. Faltava a visão de PRODUÇÃO: escala, processo, páginas geradas e publicação. Princípio: a interface é uma projeção do estado persistido, nunca uma fonte de verdade independente.

## Decisões
1. **Estados distintos, nunca equivalentes.** Oportunidade (decisão READY) → blueprint → página gerada (recipe) → QA → **aprovada** (`page_approval`, humana, vigente por versão de recipe) → **deployada** (`deployment_page` em deployment pronto) → **verificada** → (indexada: não instrumentada, sem Search Console). O estágio de cada tópico é derivado dos registros numa única consulta (`factory/pages.ts`).
2. **Métricas com definição** (`factory/metrics.ts`): cada uma declara significado, fonte, escopo e tipo (estado atual, acumulado, eventos no período, páginas únicas, versões, tentativas, deployments). Variação só existe para eventos (não há snapshots de estado). Sem instrumentação o valor é `not_instrumented`, nunca zero.
3. **Pipeline de 16 etapas** (`factory/stages.ts`) calculado dos registros reais, com a identidade total = concluídos + em execução + aguardando + bloqueados + falhas + pulados garantida por construção (aguardando é o resto) e testada. Etapas sem registro persistido (render) são "não instrumentadas".
4. **Renderer único** (`factory/render.ts`): recipe → HTML puro e determinístico, escapado, JSON-LD que não fecha a tag, links com esquema seguro. O preview (iframe `sandbox` sem scripts, larguras desktop/tablet/mobile, anotação opcional) e o deployment usam a MESMA função.
5. **Lotes** (`generation_batch` + `generation_batch_item`, migration 0020): Select → Validate → Estimate → Confirm → Generate → QA. O lote classifica antes (ELIGIBLE, BLOCKED, DATA_PENDING, ALREADY_DONE) e só ELIGIBLE vira trabalho. Execução com concorrência limitada (1–8), falha isolada por página, retentativa controlada (até 2 tentativas), cancelamento cooperativo (o item em curso termina), retomada idempotente (correlação do pipeline determinística por lote+página) e reprocessamento das páginas que pararam em revisão humana. Os contadores saem de um único agrupamento (classificação, estado, desfecho): cada item em uma caixa. Estimativa de ritmo só com ≥3 desfechos e ≥5 s; estimativa de conclusão só com ≥5 desfechos com o lote em execução. **Custo em dinheiro e tokens não são estimados nem limitados**: o provedor não os devolve a este pipeline; o limite suportado é o de chamadas ao modelo por página. Um lote não mistura proveniências: planejado como simulação, só roda com ambiente de simulação (e vice-versa).
6. **Avaliação exclusiva por tenant**: o pipeline de página espera a vez (com limite) quando outra avaliação está em curso, em vez de falhar — descoberto ao rodar o lote com concorrência 2 na bancada.
7. **Aprovação humana** (`decidePages`): exige QA_PASSED da versão MAIS RECENTE do recipe; cada página é validada e registrada à parte; aprovar não publica; tudo auditado em `decision_audit`.
8. **Deployment Center** (`factory/deployments.ts`): adaptador desacoplado da Vercel (REST v13 com `VERCEL_TOKEN`, `VERCEL_PROJECT`, opcional `VERCEL_TEAM_ID`). Regras: só entra página com aprovação vigente e QA_PASSED da versão atual; preview é o padrão; **produção exige a frase `AUTORIZO PRODUÇÃO` e motivo ≥10 caracteres**, registrados (CHECK no banco); o deployment é gravado QUEUED **antes** de chamar a Vercel; "aceito" não é sucesso: o estado vem do `readyState` do provedor (QUEUED, INITIALIZING→BUILDING, READY, ERROR→FAILED, CANCELED/DELETED→CANCELED; desconhecido não é adivinhado) e só vira VERIFIED depois que cada URL responde 200 com o `<h1>` esperado (senão fica VERIFICATION_PENDING com o motivo). Idempotência por chave (destino + projeto + versões de recipe). Atualização por polling (`refreshDeployment`); assinatura de webhook (HMAC-SHA1) e mapeamento de eventos existem e são testados, **mas não há rota de webhook** (resolver o tenant sem sessão exige credencial de serviço, que não existe).
9. **Execução assíncrona**: “Iniciar geração” responde na hora e roda `runBatch` em segundo plano (`after()`); a tela acompanha o estado gravado com atualização controlada (só enquanto há processamento). Em hospedagem serverless vale o limite de duração da função: para lotes grandes é preciso um worker/fila (pendente).
10. **Template & Module Inspector** (`/engine/templates`): contrato do pack (famílias, tipos, arquétipos, módulos, dados exigidos, visibilidade, slots editoriais, lacuna de template). Template visual, page type e page family são conceitos distintos; o LLM só preenche slots, nunca cria módulos.

## Limites declarados
- **Nenhum deployment real foi executado**: a conta Vercel acessível não tinha nenhum projeto (inspeção de 14/10/2026) e não há credenciais no ambiente. A lógica foi validada com um servidor Vercel EM MEMÓRIA (guarda os arquivos enviados e os serve na verificação), cujas respostas seguem a documentação pública e não foram capturadas de uma conta real.
- Sem `ANTHROPIC_API_KEY` nenhuma página chega a QA aprovado fora de simulação (Q14 não roda).
- Indexação não é medida (sem Search Console).
